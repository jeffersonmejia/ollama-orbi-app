# Migración de presentación a Blazor WebAssembly

Estado: **en curso; no declarar completa**.

## Decisiones y cambios de esta etapa

- Se reutiliza `src/Core/Presentation.Client`.
- Se añadió `GET /api/delivery/catalog` en `DeliveryCatalogApiController`, con filtros/paginación, datos públicos necesarios para las tarjetas, cantidades del carrito solo para el rol Usuario y datos de ubicación/dirección del usuario autenticado. La respuesta usa contratos explícitos del cliente y no expone coste unitario ni entidades EF completas.
- Se añadió el componente `Presentation.Client/Pages/Delivery/Catalog.razor` para `/Delivery` y `/Delivery/Index`: filtros con URL y debounce, resultados paginados, ajustes de cantidad por POST antiforgery y modal de dirección. La carga del catálogo empieza en el primer render interactivo del navegador para no hacer llamadas API durante prerender sin la cookie de sesión; el host registra `HttpClient` para que el prerender resuelva la inyección. La navegación «Tiendas» del shell ahora es `NavLink`; el action MVC `Index` está marcado `[NonAction]` para que esas rutas lleguen al router Blazor. Se conservan temporalmente la vista y el parcial antiguos hasta completar la comprobación en navegador.
- Se migró el carrito a `Presentation.Client/Pages/Delivery/Cart.razor` en `/Delivery/Cart`; se eliminó `Views/Delivery/Cart.cshtml` y la acción MVC GET duplicada. «Mis compras» y los enlaces entre las secciones de compra usan `NavLink` para navegar sin recargar el documento.
- Se añadió `DeliveryCartApiController`: `GET /api/delivery/cart` devuelve artículos, total y estado de dirección del usuario autenticado; `PUT /api/delivery/cart/items/{id}` actualiza cantidad (1–999); `DELETE` elimina el artículo. Las mutaciones requieren antiforgery y rol `Usuario`. El checkout conserva su lógica de negocio en el servidor y expone `POST /api/delivery/checkout`, que responde con la URL de aprobación PayPal.
- Se añadió `tests/Contract/Delivery/DeliveryCartApiContractTests.cs` al proyecto agrupado `OrbiApp.Contract.Tests`; cubre la ruta del componente, rol de acceso, antiforgery, ruta POST del checkout y límites de cantidad. No sustituye las pruebas de integración con base de datos ni PayPal.
- Se migraron `/Delivery/MyOrders` y `/Delivery/Deliveries` a páginas Blazor WebAssembly y a la lista compartida `Presentation.Client/Components/Delivery/OrdersList.razor`. La búsqueda, paginación y enlaces entre secciones usan navegación cliente; las páginas conservan restricciones por rol.
- Se añadió `DeliveryOrdersApiController` con consultas paginadas de pedidos para el cliente y entregas asignadas para el repartidor. La actualización de estado quedó en `PUT /api/delivery/deliveries/{orderId}/status`, limitada al repartidor dueño de la asignación y protegida con antiforgery; conserva el historial de estados existente. Se retiraron las acciones MVC de listado y `Views/Delivery/Orders.cshtml`; se mantiene `UpdateStatus` MVC para administración y compatibilidad de su ruta previa.
- El enlace del aside «Entregas» y los enlaces entre Carrito, Pedidos y Pagos usan `NavLink` para navegación interna.
- Se añadieron pruebas agrupadas en `tests/Contract/Delivery/DeliveryOrdersApiContractTests.cs` para rutas, roles, antiforgery, contrato de actualización y retiro de las acciones MVC de listado.
- Se migró `/Delivery/MyPayments` a `Presentation.Client/Pages/Delivery/MyPayments.razor` y se agregó `GET /api/delivery/payments`. El endpoint limita las filas al correo autenticado, conserva búsqueda y paginación de 12 elementos y entrega solo los campos que muestra la pantalla; no expone el identificador externo de PayPal. Se retiraron la acción y vista MVC de pagos del cliente, el parcial MVC de navegación y los enlaces «Pagos» de carrito/pedidos ahora son `NavLink`.
- `tests/Contract/Delivery/DeliveryPaymentsApiContractTests.cs` cubre la ruta cliente, la restricción por rol y el retiro de la acción MVC de pagos.
- Se migraron `/Identity/Account/Manage` y `/Identity/Account/Manage/Addresses` a componentes cliente `Pages/Identity/Manage/{Profile,Addresses}.razor`. Perfil solicita solo usuario/correo/verificación/rol/teléfono; Direcciones solicita sus datos y opciones de ubicación al visitar esa sección. Las operaciones usan endpoints autenticados de `IdentityAccountApiController` y `IdentityAddressesApiController`; las mutaciones requieren antiforgery. Se retiraron las páginas Razor de perfil y direcciones, y el enlace del aside a Perfil ahora usa `NavLink`.
- La navegación de cuenta comparte `Components/Identity/AccountManageNavigation.razor`; Perfil y Direcciones navegan dentro de WASM. Pagos y Seguridad todavía usan Razor Pages mediante enlaces de carga completa. Se conservan edición, validación, selección de provincia/ciudad, asignación de dirección principal y bloqueo de eliminación de la principal.
- `tests/Contract/Identity/IdentityAccountApiContractTests.cs` comprueba rutas cliente, autorización de API, verbos y antiforgery en mutaciones, además de validación de teléfono, correo y dirección.
- `src/Core/Presentation/Components/App.razor` asigna `InteractiveWebAssembly` a `Routes` y `HeadOutlet`.
- La pantalla estática `Home/Privacy` se trasladó a `Presentation.Client/Pages/Home/Privacy.razor`, conserva `/Home/Privacy` y se retiraron su vista y acción MVC. No necesita endpoint de negocio.
- Se migró la portada pública `/` a `Presentation.Client/Pages/Home/PublicHome.razor`, conservando el video y su control de sonido. El componente envía al rol Usuario a `/Delivery` y mantiene las rutas MVC de los demás roles; el estilo está en `wwwroot/css/features/home/public-home.css` y no agrega sombras.
- Se quitó el registro y endpoint de Interactive Server: `AddInteractiveServerComponents()` y `AddInteractiveServerRenderMode()` ya no forman parte de la configuración. El shell Blazor no debe abrir circuitos SignalR.
- MVC/Razor Pages y sus rutas se mantienen temporalmente porque sus pantallas aún no tienen reemplazo funcional. La navegación cliente se cambia por módulo una vez portadas las rutas y operaciones correspondientes.
- Secretos, conexión a base de datos, reglas de negocio y autorización siguen en backend. El cliente debe llamar APIs con cookie HttpOnly de mismo origen y antiforgery en mutaciones; no incluir secretos en el bundle.
- La auditoría inicial encontró endpoints JSON para contexto de sesión y opciones de registro en `WebApplicationExtensions.cs`. La mayoría de las acciones de negocio son acciones MVC que devuelven vistas, redirecciones o parciales; requieren contratos API antes de consumirlas desde WASM.

## Verificación y limitaciones observadas

- Inspección estática de `.csproj`, `Program.cs`, `App.razor`, `Routes.razor`, `_Imports.razor`, registros de servicios, rutas del host y pantallas fuente.
- `rg` confirma que `InteractiveAuto` y `InteractiveServer` ya no aparecen en el shell; siguen registrados los servicios y el endpoint de Interactive WebAssembly.
- `git diff --check` no encontró errores de whitespace; Git mostró solo avisos de normalización LF/CRLF. Las búsquedas fuente ya no encuentran las acciones MVC `MyOrders`/`Deliveries`/`MyPayments`, las vistas MVC de pedidos/pagos del cliente ni el parcial `_PurchasesNav`; la búsqueda previa tampoco encontró la acción ni la vista MVC `Privacy`.
- Se agruparon los proyectos de prueba por tipo en `tests/Contract`, `tests/Integration` y `tests/Performance`; `OrbiApp.slnx` ahora incluye esos tres proyectos.
- `dotnet build OrbiApp.slnx --no-restore --artifacts-path "$env:TEMP\orbi-full-solution"` compiló toda la solución después de migrar la portada pública: 0 errores. Permanecen avisos NU1902/NU1903 de `System.Security.Cryptography.Pkcs` y CS8604 en `FeatureViewLocationExpander`; la salida de Sonar indica que falta `.sonarqube/bin/targets/SonarQube.Integration.targets` localmente.
- `dotnet test tests/Contract/OrbiApp.Contract.Tests.csproj --no-build --no-restore --artifacts-path "$env:TEMP\orbi-full-solution"` pasó: 20 pruebas, 0 fallos. Esto valida contratos estáticos; no sustituye pruebas de integración de API ni flujos autenticados en navegador.
- No se ejecutaron las pruebas de `tests/Integration`: `ORBI_DATABASE_TEST_CONNECTION` no está configurada y no hay PostgreSQL escuchando en el puerto local aislado `55433` requerido por `PostgresDatabaseFixture`.
- Antes de añadir el carrito, `GET http://localhost:5175/Delivery` respondió `302` hacia Login sin cookie de sesión y `/api/delivery/catalog` respondió `401` anónimo. Tras los cambios, `5175` dejó de aceptar conexiones durante la comprobación; no se reinició el backend. Los endpoints nuevos de identidad también respondieron como no disponibles en la comprobación anónima actual; los flujos autenticados de perfil/direcciones quedan pendientes de verificación en navegador.
- Se confirmó mediante reflexión del ensamblado cliente que `Catalog` contiene `/Delivery` y `/Delivery/Index`. El host añade el ensamblado cliente mediante `AddAdditionalAssemblies(typeof(_Imports).Assembly)`. Falta una prueba autenticada de catálogo y carrito, filtros, dirección, cantidades y checkout.
- `NavigationProgress` registra `LocationChanging` solo cuando `OperatingSystem.IsBrowser()` es verdadero; antes de esa guarda, el prerenderizado HTTP fallaba con `NotSupportedException` de `HttpNavigationManager`. Los registros históricos todavía contienen esas fallas anteriores al cambio, por lo que no se consideran evidencia de estado actual.
- No se pudo comprobar el render autenticado en navegador: el host de automatización del navegador no está disponible en esta sesión. Siguen pendientes pruebas funcionales, medida del bundle WASM y verificación completa de navegación interna e interacciones entre módulos.
- El goal queda acotado por instrucción del usuario al rol Usuario y a las vistas públicas; la migración de Administrador, Vendedor y Repartidor no se incluye en esta etapa.
